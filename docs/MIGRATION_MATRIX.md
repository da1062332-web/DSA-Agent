## Numbering and history

- **Gaps** (0008, 0009, 0012 to 0018, 0038, 0039) are numbers never used; they are not missing files.
- **0043 / 0063:** `0043` was used by two files. The security migration (`security_monitoring_incidents`, manifest M-063) was renumbered to `0063`, content byte-identical (SHA-256 `5eeccafb…12b8`); `0043_integrations` (applied on hosted) keeps its number. Nothing was run on hosted, and the security tables do not exist there, so no hosted state depends on the old number. `migration-versions.spec.ts` now has no known duplicates.
- **0050 / 0064:** the sanction/disbursement grants were renumbered from a second 0050 to 0056 and then to 0064, because the ledger migration was published as 0056 (content byte-identical, hash `9cb37ea9…`). A fresh build gives the same permissions and grants in either order (checked). Hosted already has the effects, so nothing is re-run there. The ledger migration (0056) is not applied on hosted and is Release 3.
- **Edits to merged migrations.** The project rule is "a merged migration is never edited". Two were edited in place, deliberately: `0055` (its rule rows violated the table check, so it failed on every fresh database and was never applied anywhere) and `0051` (it granted `customer.create` and `customer.update`, which no migration defined). Both are idempotent (`ON CONFLICT DO NOTHING`), so a database where they ran partly simply completes. Neither is applied on hosted, so no applied migration changed. This is a documented exception, to be approved by the owners.

## Reconciling history safely (not done, needs your approval)

1. Do not rename, reorder or replay anything on hosted. A file name does not change hosted state.
2. If migration history is adopted, create it from verified facts: `supabase migration repair --status applied <version>` ONLY for versions this matrix shows applied, (the 0043 duplicate is now renumbered). The repair writes history; it does not run SQL.
3. Apply pending migrations one at a time through `node tools/sql/make-apply-run.mjs <migration> ~/dsa-backups/<n>/`, which writes a `BEGIN; ... COMMIT;` wrapper outside the repository and prints the source and wrapper SHA-256. Run `tools/sql/batch/preflight.sql` first, then the migration, then `tools/sql/batch/<n>.verify.sql`; `tools/sql/batch/<n>.rollback.sql` backs it out. 0054 has its own package in `tools/sql/0054`. Full commands, expected results and what each rollback keeps: `tools/sql/batch/README.md`.
4. Suggested order: 0054, 0057, 0059, 0060, 0061, 0058, then 0055 (after the `eligibility.override` roles are confirmed), then 0063, and 0062 only if the executor is wanted. **Rehearsed on PostgreSQL 16 and 17** (`migration-sequence.int.spec.ts`, `migration-batch-runbook.int.spec.ts`): there is no technical dependency between these migrations. Each applies alone on the hosted state, and the proposed order, its reverse, the numeric order and two shuffles all end in an identical database. The order is a risk choice (small and reversible first, the decision-dependent 0055 late), not a requirement.
