## 4. Working rules

These come from `CLAUDE.md`, from the contracts README, and from the developer's standing rules.

- **Branches and PRs:** `d<N>/TASK-nnn-short-name`. One task per PR, about 400 lines or fewer. Exceptions need A-DEV.
- **Commits:** Conventional Commits with the task ID, for example `fix(finance): refuse status in commission plan PATCH (SEC-01)`. No `Co-Authored-By` or "Generated with" trailers in commits or PR descriptions.
- **Never commit** `.env` files or secrets. Only `*.env.example` placeholders are committed.
- **No force push** and **no history rewrite** without A-DEV and A-SEC. The rewrite decision is recorded separately.
- **Shared contracts** (`packages/contracts`): additive changes only. When something must break, add an `@deprecated` shim that stays for one release. Approval from the affected owners, and a line in the Contracts §15 change log.
- **Migrations:** never edit a merged file. A new migration goes in the owner's number range, and `supabase/migrations.lock.json` is updated by the tool. `npm run check:migrations` must pass.
- **Hosted database:** no write, delete, migration, role change or key rotation without written approval in the same thread. Read-only checks come first, and their results are recorded.
- **Secrets:** never printed in logs, tickets or documents. Names only. Rotation follows `docs/SECURITY_CREDENTIAL_ROTATION.md`.
- **Tests:** each change names its test IDs. The regression test is written first and fails before the fix.

## 15. Rollback

| Change type | How to roll back | Limits |
|---|---|---|
| Code PR | Revert the PR. Redeploy the previous commit | Revert does not undo data written by the new code. Check the data first |
| Configuration | Restore the previous variable value | Changing a secret value makes data encrypted or hashed with the old value unreadable or unmatched. Do not roll back a key change without the data plan from SEC-03 |
| Hosted migration | Run the matching rollback script in `tools/sql/batch/`, as the runbook describes | Rollback scripts refuse without a snapshot. They never drop data |
| Ledger reconciliation | Mark a version reverted, with `supabase migration repair --status reverted` | Only for versions recorded in error. Dropping the ledger table needs its own approval |
| Key rotation | Keep the old value available until the new value is verified | After a value has been exposed, do not restore it |
| Contract change | The `@deprecated` shim keeps the old field for one release | Removal is a separate release |
