## Decisions that remain with the business

1. F3: connector verification records, or an explicit rule for what a VERIFIED record means for a connector.
2. F4: accept that a duplicate refusal confirms an open enquiry.
3. Application and lender progress labels: `docs/CONNECTOR_PHASE1_CONTRACT.md` section B. Until approved, partners see only the lead-level steps.
4. Which document types partners may send (`document_type.partner_upload`).
5. Whether staff with `lead.read` may see a referral's customer name on the connector workspace (today they do, and the mobile number is hidden).
6. Dispute evidence attachments: not built. Existing uploads are tied to checklist items, and a dispute has no checklist. A new subject type is needed first.

## Not verified here

- No browser test was run. The new screens are verified by component tests that render them, not by looking at them on a phone or desktop.
- The OpenAPI document (`openapi/openapi.yaml`) was regenerated on 2026-11-02 and now lists the new routes: connector summary, connector referrals, connector activity, the partner referral detail, the partner document list, the partner upload intent, the partner upload completion, and the portal disputes list. The regeneration also picked up the earlier changes (`partnerUpload` on document types, the required `category` on portal disputes) and run-date default values in two schemas. The isolation inventory checks the `/v1` operations (4 of 4 pass). The `/portal/v1` operations are not covered by the isolation sweep.
- The hosted scanner configuration (`CLAMAV_ADDRESS`) has not been checked. Partner uploads stay disabled on hosted until an authorised operator confirms it.

## Changes since this audit

- **Second-factor setting (F23).** The web app used to find out whether the project had authenticator sign-in off from Supabase error codes, and then sign people in without a second factor. It now reads `SUPABASE_MFA_ENABLED` from the API (`GET /public/v1/auth/config`) before any sign-in. When the API asks for a second factor and the sign-in service has none, sign-in ends with a message instead of continuing. Tests: `apps/web/src/auth/mfa-flow.spec.ts`, `apps/web/src/auth/auth-config.spec.ts`, `apps/api/test/auth-config.spec.ts`.
- **Step-up with second factors off.** When `SUPABASE_MFA_ENABLED=false`, the API skips step-up for sensitive actions, including payouts, because no second factor can be asked for. That is the existing design, and it is a deliberate operator choice.
- **OTP module follows the setting (F23).** With second factors off, the sign-in, the dev test-login, the step-up dialog and the security page's set-up controls never show an authenticator code step. With them on, the code step runs as before.
- **Migration rollbacks need provenance (F24).** The grant table keeps no record of who added a row, so the 0098 and 0099 rollbacks use snapshots taken by the runbook before each apply, and refuse without them. They also require an operator's confirmation in the session, since a grant made by hand cannot be seen from the database. Rehearsed in `apps/api/test/migration-0098-0099.int.spec.ts` (9 of 9).
- **Invitation resend (F22).** The root cause is now covered by a regression test: TEST-WRK-11 fails on the old worker-clock comparison and passes on the database-clock check. The test was run against the old code to confirm this.
- **Signed file links (F21).** Regression tests in `apps/api/test/file-link-signer.spec.ts` cover the canonical signature, the exact segment count, and tampered bodies.
